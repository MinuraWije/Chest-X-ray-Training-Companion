# Phase 2 — MedGemma + RAG

> **Status:** planned, not started. Written 12 September 2026, after the Phase 1
> production path was changed to supply the confirmed finding to the model
> (prompt `p2.4`). Companion to `docs/plans/2026-09-05-medgemma-support.md`.
> `docs/DEVELOPMENT_PLAN.md` covers Phase 1 only; its §11 previews Phase 2 in
> four bullets. This document is that phase in full.

---

## Context

Phase 1 is functionally complete: 6 of 10 milestone items DONE, 3 PARTIAL, 1 NOT
DONE. Three roles enforced, the full register→login→case→attempt→feedback path
working, live MedGemma over the Kaggle tunnel at 100% structure validity, 300
curated NIH cases, 384 backend tests, 28 report artefacts.

Phase 1 also changed direction in a way that defines Phase 2. The model is now
**given** the case's confirmed finding rather than asked to diagnose it, because
recognition sat at 16–25% across six prompt strategies against a 16.7% chance
floor. The product is a tutor marking a student's interpretation, not a
classifier. Phase 2 makes that tutor cite published evidence instead of speaking
from the model's own memory.

**Outcome:** feedback cites passages from a licence-cleared published source;
`reports/phase2_eval.md` compares five arms on citation fidelity, retrieval
relevance, abstention and passage-induced confabulation.

### Three constraints that shape everything

**1. The system prompt is full.** The notebook server caps `system` at 4000
chars and `prompt` at 8000 (`kaggle_runtime/medgemma_server.py:86-87`). The
worst rendered system prompt across the real manifest is **3982 chars — 18
characters of headroom**. Passages go in the **user turn**, and anything added
to the system turn requires trimming it first.

**2. The eval harness cannot evaluate this.** `infrastructure/eval/__init__.py`
deliberately bypasses `SubmitAttemptUseCase`, uses its own bias-free prompts,
and passes **no student free text at all**. The misconception-keyed retriever's
entire input *is* student free text. Phase 2 needs a second evaluation path;
the existing classification harness stays frozen so the e1.0–e5.0 reports
remain valid.

**3. There are no student answers to evaluate against.** Every probe so far used
one hard-coded sentence. Marking behaviour cannot be measured without a fixture
set, and that blocks the whole phase.

### What already exists (no work needed)

`RetrievedPassage` and `Feedback.sources` (`domain/entities/feedback.py:30-44`,
`:74`), SQLite JSON round-trip both ways (`sqlite_attempt_repository.py:50-53`,
`:85-88`), API DTO emission, TypeScript types (`frontend/src/types/api.ts:30-48`),
a rendered sources panel (`FeedbackSection.tsx:64-78`), and the educator rubric's
`retrieval_relevance` / `evidence_grounding` criteria (`domain/entities/review.py:10-19`).

Useful scoping fact: the corpus is **50 cases each of pneumothorax,
pleural_effusion, cardiomegaly, consolidation, nodule_or_mass and no_finding** —
there are **no fracture cases at all**. Corpus coverage is needed for five
positive findings, not seven.

## The arm design — settle this first, everything follows

Moving retrieval *and* changing the prompt at once makes every Phase 2 result
un-attributable: "different prompt + retrieval" is not "retrieval". Five arms:

| Arm | What it isolates |
|---|---|
| **p2.4** | frozen Phase 1 baseline |
| **p3.0-empty** | new prompt, passage block rendered empty, retrieval off — **the control** |
| **p3.0-oracle** | finding-keyed: confirmed category → its chunks. An upper bound, not a retrieval result |
| **p3.0-bm25** | unfiltered BM25 over the whole corpus — the only arm yielding a non-circular relevance number |
| **p3.0-misconception** | BM25 + boost on what the student got wrong |

`p3.0-empty` is non-negotiable. It attributes the prompt change separately from
retrieval, and it is the baseline the confabulation metric subtracts against.

## Step 2 — The corpus (start in parallel with Step 1; highest schedule risk)

`data/corpus/*.md`, one file per source, chunk = an authored `##` section. No
chunking algorithm — one fewer free parameter to defend.

**Primary source:** *The WHO Manual of Diagnostic Imaging: Radiographic Anatomy
and Interpretation of the Chest and the Pulmonary System* (Ellis & Flower, WHO
2006, ISBN 9789241546775), 147 pages, on WHO IRIS at
`https://iris.who.int/handle/10665/43293`. Covers pattern recognition and our
findings directly.

**Licence — verify, do not assume.** WHO IRIS content is generally
CC BY-NC-SA 3.0 IGO (non-commercial, attribution, ShareAlike), which fits an
academic artefact — but this 2006 publication predates WHO's open-access policy,
so read the PDF's actual copyright page first. Two rules regardless: **text
only, never the radiographs** (images in WHO publications are often third-party
and need separate permission), and record provenance per chunk. Fallback if
restrictive: StatPearls (CC BY 4.0). Supplement to 50–80 chunks across the five
positive findings; discover any coverage gap in week one, not week five.

Front-matter, with `licence` enforced against an allowlist by the build script —
a chunk with an unapproved licence is **refused, not warned about**:

```yaml
id: who-2006-p42-effusion-signs
source: "WHO Manual of Diagnostic Imaging (Ellis & Flower, 2006), p.42"
url: "https://iris.who.int/handle/10665/43293"
licence: "CC BY-NC-SA 3.0 IGO"
licence_url: "https://creativecommons.org/licenses/by-nc-sa/3.0/igo/"
retrieved_on: "2026-09-12"
findings: [pleural_effusion]
confusions: [consolidation, elevated_hemidiaphragm]
aspect: radiographic_sign      # | differential | pitfall | management
```

`aspect` exists because topical ≠ pedagogical: a chunk about ultrasound-guided
drainage is tagged `pleural_effusion` and useless to someone reading a film.
Relevance is reported restricted to `aspect != management`.

**Chunks capped at ~700 chars** so three passages plus student text fit the
8000-char user turn.

`backend/scripts/build_corpus.py` — extracts, validates every front-matter key,
enforces the licence allowlist, records a sha256 of each source document
(mirroring the existing `data/raw/PROVENANCE.json` pattern), writes
`data/corpus/index.json`. `--check` mode for CI. **PyYAML and pypdf go in
`requirements-dev.txt` only** — the build is offline, the runtime reads
`index.json`, so the 13 runtime dependencies genuinely do not change.

## Step 3 — BM25 (test first; silent-correctness risk)

Pure-Python Okapi BM25, `k1≈1.2`, `b≈0.75`, zero new runtime deps.
`infrastructure/retrieval/`: `corpus.py`, `bm25.py`, `bm25_retriever.py`,
`category_retriever.py`.

A subtly wrong length normalisation degenerates toward "return the longest
chunk", is invisible in output, and silently invalidates every reported number.
**Write the ranking test against a hand-built toy corpus with a known expected
order before the implementation.**

**Score normalisation: `score = bm25 / (bm25 + k)`**, saturating and absolute.
Not top-1 normalisation — that makes the best hit 1.0 even when BM25 gave it
nearly nothing, so the UI would render "score 100%" beside a garbage match in a
medical teaching tool, and it makes thresholding (and therefore abstention)
impossible. Raw BM25 goes into `Feedback.raw` under `retrieval: [{id, bm25,
rank}]` regardless of what is displayed. Keep `RetrievedPassage`'s `[0,1]`
validation — it is doing real work.

**Consider showing the student no number at all.** A percentage beside a
citation implies a reliability it does not carry. Rank, or nothing.

**Port change:** `retrieve(*, query: RetrievalQuery, top_k: int = 3)` where
`RetrievalQuery` carries `free_text`, `confirmed_categories`, `named_categories`,
`case_id`. A struct rather than adding a `categories` kwarg, because we already
know two strategies need different signals and would otherwise widen the
signature once per signal. `NullRetriever` updated to match.

**`RetrievedPassage` gains `id` and `url`** (defaulted). `source` is not unique
— two chunks from one document collide, and `FeedbackSection.tsx:71` already
keys on `` `${s.source}-${s.score}` ``, which will produce duplicate-key
warnings. Blast radius ~8 files: repository both directions, both DTO shapers,
TS types, the component.

**Composition root:** `get_retriever()` (`dependencies.py:114`) takes no
`Settings` and builds a fresh instance per request. It becomes settings-aware
and `@lru_cache`d (following `_tunnel_client` at `:126-129`) and is added to
`reset_dependency_caches_for_tests()` at `:188`. New settings:
`RETRIEVAL_RUNTIME=null|oracle|bm25|misconception` and `CORPUS_DIR`.

## Step 4 — Misconception detection, deterministically

Prose → misconception is itself classification, and this model measured 16–25%
on an easier 7-way task. So do not use the model:

- **L0:** BM25 on the free text, plus a boost for chunks whose `confusions` tag
  matches a category the student **named** but the case does not confirm. Alias
  matching against 7 known categories — ~40 lines, auditable.
- **L1:** flag `missed` when the confirmed category's aliases are absent from the
  student's text.

Write it up as a **lexical proxy for** misconception detection, with failure
cases stated. **The nastiest bug is negation:** "there is no pneumothorax"
alias-matches `pneumothorax` and retrieves pneumothorax material for a student
who correctly ruled it out. Handle it explicitly and test it.

## Step 5 — Retrieval moves before generation

Today `_attach_retrieval` (`submit_attempt.py:138-146`) runs *after* the model
has written its text. Passages therefore ground nothing, and a grounding metric
over a post-hoc attachment measures only whether prose written in ignorance
happens to agree with a document it never saw.

Retrieval moves into `_generate_feedback` before `analyze_and_parse`; passages
render into the user turn as **opaque `[S1] [S2] [S3]` labels**; `Feedback.sources`
records what was supplied; `retrieval_mode`, `retrieval_k` and `corpus_version`
join `prompt_version`/`model` in `Feedback.raw` — a stored row you cannot
regenerate is not provenance.

On G2: the plan claims adding RAG needs "zero changes to domain or use-case
layers". The correction is that **no ports change and the domain does not
change**; one private method of one use case does. Orchestration is what the
use-case layer is for, and a plan claiming the orchestration layer never changes
when the orchestration changes was overclaiming. Say so in the report rather
than defending it.

**The p3.0 prompt needs a new rule.** Passages describe findings **in general**;
the image is **this patient**. Never assert a passage's feature is visible on
the film. This is not theoretical: p2.2 showed that telling this model to look
for a second finding made it invent one — a confirmed pneumothorax reported as a
pleural effusion, its physical opposite, reproducibly across three prompt
versions. Handing it a passage describing effusion is the same attractor with a
stronger pull.

**Abstention.** Below an absolute score floor: supply no passages, tell the model
no reference material was supplied, render nothing (`FeedbackSection.tsx:64`
already handles empty). Do **not** show weak sources for completeness. Keep the
existing `except Exception → warn → continue` so a broken index degrades to
Phase 1 rather than failing a submission — but note this means the eval must
assert non-empty sources or it will measure nothing and report success.

**Citation enforcement, mirroring `_enforce_ground_truth`:** strip any `[Sn]` the
model names that was not supplied, before it reaches the student; log the
override; let the eval read the rate. Same pattern, same justification,
consistent architecture story.

## Step 6 — Metrics and the comparison report

A second evaluation path, `run_feedback_evaluation`, going through
`PromptBuilder` over the Step 1 fixtures. The existing classification harness
stays frozen.

| Metric | Definition | Why |
|---|---|---|
| **Citation validity** | % of named `[Sn]` that were actually supplied | The confabulation thread, directly |
| **Citation rate** | % of feedbacks citing ≥1 passage | A model citing nothing scores 0% hallucination — perfect and useless. Report the pair |
| **Passage-induced confabulation** | rate at which feedback asserts an image feature present in a supplied passage but *not* asserted by `p3.0-empty` on the same case | The headline. Only the control arm makes it computable |
| **Precision@3** | tag-overlap, `aspect != management` | **`p3.0-bm25` only.** Tags did not participate in its ranking |
| **Abstention rate** | % of cases below the score floor | A system that knows when it has nothing is a better artefact than one with higher precision |
| **Corpus coverage** | distinct chunks ever retrieved across the eval set | Exposes the small-corpus degeneracy where 3 chunks serve every case |
| **Lexical overlap** | content-word Jaccard, vs a **shuffled-passage control** | Overlap without a null is uninterpretable |

**Do not report precision@k for `p3.0-oracle`.** It filters on the same tag it
would be scored against, so precision is 1.0 by construction, falling below 1.0
only when the corpus has fewer than k chunks for that category — that measures
corpus coverage and calls it retrieval quality. Report it as an upper bound
answering "does supplying *correct* evidence improve feedback?"

**If time allows (half a day, high value):** hand-label relevance for ~30 cases
× top-5 = 150 judgements, then validate the automatic tag-overlap proxy against
them. "My cheap automatic metric agrees with my manual labels on 82% of pairs"
is far stronger than either metric alone.

**Latency is not comparable to the e-series** regardless of how it is measured —
the p3.0 prompt is longer, so model latency rises legitimately. Report Phase 2
latency as its own baseline and compare only within Phase 2. Record
`prompt_chars` per sample. Retrieval latency gets its own field; the existing
timer wraps the whole try-block (`:808`–`:853`).

Defaulted fields on `EvalSample`/`EvalReport` (both frozen `slots=True`):
`retrieval_latency_ms`, `retrieved_ids`, `relevant_at_k`, `cited_ids`,
`hallucinated_ids`, `abstained`, `corpus_version`, `retrieval_mode`,
`prompt_chars`. Extend `_build_report`, `_empty_report`,
`render_markdown_summary` and `__all__` in step.

## Tests

Conventions: `from __future__ import annotations` first, full annotations
(mypy --strict), hand-rolled doubles — **`unittest.mock` is used nowhere** —
class-based grouping past ~4 cases.

- BM25 ranking against a toy corpus with a known expected order (**write first**);
  length normalisation does not favour long chunks; empty query; no match.
- Normalisation: bounded in [0,1); monotone in raw score; single result safe.
- Corpus loader: refuses a missing front-matter key, an unknown `findings` tag,
  an unapproved licence, an over-length chunk.
- Misconception: negation ("there is no pneumothorax") does **not** trigger the
  pneumothorax boost.
- Use case: passages reach the prompt; retrieval failure degrades to no sources
  and still returns feedback; a fabricated `[Sn]` is stripped and logged;
  abstention supplies nothing.
- `StubRetriever` in `tests/support/doubles.py` (none exists).
- **Prompt budget regression test:** rendered system < 4000 and user < 8000 for
  every manifest case. Current margin is 18 characters; without this the next
  prompt edit ships a 422.
